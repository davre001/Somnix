# SOMNIX — Limitations

This document lists the deliberate engineering trade-offs, constraints, and known limitations of SOMNIX, stated plainly rather than left for a reviewer to find.

---

## 1. Environment & Network Scope
- **Somnia Shannon Testnet Only**: SOMNIX is configured for Somnia Testnet (`chainId: 50312`). It is not deployed on mainnet.
- **Native STT vs. collateral are different assets**: `STT` is the native gas token (used for network fees and shown as-is in wallet/network UI). The DreamDEX binary markets settle in a separate ERC-20 collateral token, whose real `symbol`/`decimals` are read on-chain once (`somnia.ts#fetchCollateralMeta`) and used for every lock amount, balance, and payout figure in the app. Don't assume it's `STT` — check what the app actually resolves it to at runtime.
- **Verified end-to-end against a live wallet, live order book, and live testnet claim on 2026-09-03.** Using `frontend/scripts/live-cycle.mjs` (a `live:`-prefixed script — see `package.json`, never run in CI), a throwaway funded wallet locked 5 tUSDC on a real BTC 1h window (fill price 0.843, tx `0x5ade91...`), the window resolved Green on-chain, and the position was claimed for a real payout (tx `0xbd67ef...`) — collateral balance moved 10,000 → 10,000.965 tUSDC, exactly matching the expected 1:1 outcome-token redemption. This also surfaced and fixed a real bug: `exchange.redeem()` resolves markets through the SDK's live-markets registry, which explicitly excludes finalized (resolved) markets by design — so the original claim path failed with "unknown market ref" on every real claim, regardless of calling `loadMarkets()` first. Fixed in `exchange.ts#claimWinnings` by reading the market directly by id and calling the raw `trader.redeem()` instead, bypassing the registry. One external dependency was also observed failing during this test (the indexer's `Market_by_pk` query timing out entirely, independent of any code here) — see `docs/API_NOTES.md` for that caveat; it is not something this app controls.

## 2. Market Windows, Pairs & Real Liquidity
- **Supported Pairs**: BTC and ETH.
- **Window lengths offered**: `1m`, `3m`, `5m`, `15m`, `1h`. All five are real, tradable cadences as far as the code is concerned — nothing is hardcoded to disable a length. Whether a given pair+length is *actually* tradable at any moment depends entirely on whether DreamDEX (or an operator) currently has a live `BinaryMarket` on that exact cadence; the app has no market-creation authority of its own.
- **Honest liquidity gating, not a fallback**: `marketService.ts#getMarketWindow` returns `isLive: false` by default. Only `fetchLiveMarkets` finding a real DreamDEX market for the exact pair+interval flips a window to `isLive: true`, and only then does `lockValidation` allow locking it. When no live market exists for a selection, the UI disables locking with an explicit reason ("No live DreamDEX market for this window right now") — it never silently falls back to a synthetic/simulated market to make locking possible.
- **A "lock" is a real market order against a real order book.** If the opposite side of the book has no resting liquidity, the order will fail (`InvalidInputError` from the SDK) rather than fill against nothing. This is expected, correct behavior on a thin testnet book, not a bug — but it means "which windows are actually lockable right now" is an operational fact about DreamDEX liquidity, not something this repo controls.
- **Cutoff Times**: A lock cannot be submitted in the final moments of a window (`10s` for 1m, `20s` for 3m, `30s` for 5m, `60s` for 15m/1h) to avoid a transaction landing after the window closes.

## 3. Account & Custody Model
- **Non-Custodial**: SOMNIX holds zero user funds and zero private keys — nothing server-side can move, freeze, or gate a user's position. A local state (active lock, pending-lock intent, recents) lives in the user's browser `localStorage`, and a separate Turso (libSQL) table, written from this app's own `app/api/*` route handlers (non-authoritative), mirrors lock/claim *history* after the fact — see §6.
- **Browser-specific, but reconciled against the chain, not just trusted.** If a tab closes between the wallet confirming a lock and the app recording it, the position isn't silently lost: a pending-lock intent is persisted *before* the wallet prompt (`marketService.ts#savePendingLockIntent`) and reconciled against the wallet's real outcome-token balance the next time a signer binds (`lib/hooks/useLock.ts#reconcilePendingLock`, `exchange.ts#checkFilledAmount`). This is best-effort, not a guarantee: reconciliation only runs on this device, in this browser, the next time the same wallet connects here. If a user never reopens the app on this browser/device, the reconciliation never runs, though the funds/position themselves are unaffected on-chain — only the app's UI record of them would be missing.
- **A void market redeems either side at par.** `claimPayout` doesn't gate a claim on "did my side win" when the market voided — it proceeds regardless of predicted side, matching the protocol's void-redemption semantics.

## 4. Single Lock Per Window
- **UX constraint, not a protocol one**: the app allows only one lock per `marketId` at a time (checked client-side in `lockValidation`), to keep the "one deliberate call per window" experience. This is enforced in the UI only.

## 5. Display-only gaps
- **A lock's `startPrice` is now the market's real, oracle-recorded strike price** (`exchange.ts#getRealStartPrice`, reading `market.info.strike` off the same `UnifiedMarket` `findLiveMarket` already fetched at lock time — no extra network call), not a placeholder. The oracle's numeric price scale (2 decimals) isn't documented anywhere in the SDK's types — it was verified empirically by comparing `strike` against real BTC/ETH spot price across 11 samples (5 resolved + 1 live market each for BTC and ETH), every one landing within 0.1% of spot. Reproduce with `node scripts/inspect-oracle-price.mjs [--asset=BTC|ETH] [--intervalSec=60|180|300|900|3600] [--live]`. Falls back to `marketService.ts#getMarketWindow`'s synthetic seed only if `getRealStartPrice` ever returns null (a non-binary market, or a market somehow missing a strike) — this fallback has not been observed in practice. Locks recorded before this fix keep whatever synthetic value they were created with; this only affects new locks going forward.
- **No real "Settlement Price" is available for these markets.** The SDK also exposes `client.getMarketResolution(marketId)` → `openingAnswer`/`closingAnswer` (a would-be real closing price), but both came back `null` on every one of the same 11 samples — this operator/venue's oracle apparently doesn't populate the reference-question numeric answer at all for these up/down markets. `exchange.ts#getResolution`'s `endPrice` (checked against `market.closingPrice`) is left as `undefined` in this case, and `RevealPanel` correctly shows "—" rather than fabricate a number — that blank is honest, not a bug. Settlement (win/lose) is entirely determined by the real on-chain `winningOutcome`/`payoutNumerators` regardless, never by a price comparison in this app.

## 6. Server history mirror — a record, not a source of truth
- `POST /api/lock`/`/api/claim` (Turso-backed) only ever gets fed real, already-confirmed data — never a pre-trade estimate — and the reported `txHash` is checked against the real chain (`lib/server/chainVerify.ts`) before it's persisted. See `docs/API_NOTES.md` §5 and `docs/THREAT_MODEL.md` Threat 7.
- **What it doesn't do**: verify the exact `filledAmount`/`fillPrice` reported alongside a valid `txHash` — that would require decoding the CLOB fill server-side, which is disproportionate for a store that authorizes nothing. A user's actual position and any claim are always decided by the real chain, never by this table. **This is now surfaced in the UI, not just this doc**: `RecentsList.tsx` labels each played round's locked amount "self-reported" (hover for why) — the win/loss badge next to it stays fully trustworthy (derived from a live `getResolution` read, see the point below), only the dollar figure itself carries the caveat.
- **No resolution outcome is persisted.** `LockRecord` deliberately has no `resultSide`/`won`/`lost` field — RevealPanel and RecentsList always derive the outcome from a live `getResolution` chain read rather than trusting a second, potentially-stale copy. A cross-device "recents" view built on this store would need its own live resolution lookup per item, same as RevealPanel does today — it doesn't get one for free from the server.
- **Cross-device history is opt-in-by-connection, not automatic.** The mirror only has what was successfully reported from *some* browser session for that wallet; a device that was offline when a lock/claim happened, or whose report failed, has nothing to show until/unless another session reports it.
- **Rate limiting is in-memory and per-instance, not shared/global** — a per-IP, per-route fixed-window cap exists on every server surface (`lib/server/rateLimit.ts`, wired through `apiRoute`'s `rateLimit` option), but it resets on every cold start and isn't coordinated across concurrent instances. See `docs/THREAT_MODEL.md` §3.
- **Turso must actually be configured for this to survive a real deploy.** Without `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN` set, `lib/server/tursoStore.ts` falls back to a local `file:local.db` — fine for `pnpm dev`, but a serverless deploy has no durable local disk, so every cold start would start that fallback db over empty. This has not been exercised against a real Turso database as of this writing — same caveat as §1's live-trading-path gap.
- **The libSQL `Row` object is array-like** — a column read back by a name that collides with a real `Array`/`Row` property (e.g. `length`) silently returns the wrong thing instead of erroring. `lib/server/tursoStore.ts` works around this for the one field that collided (`windowLength` in SQL, still `length` in the TS `LockRecord` type) — caught by `tursoStore.test.ts`, not by inspection. Worth remembering before adding another column.

## 7. Lock sizing bug, fixed 2026-09-06 — pending final live re-verification
- **The bug (real money, not display)**: `lockPosition` used to pass the user's typed dollar amount straight into the unified `exchange.createOrder(...)`'s `amount` parameter, which the SDK treats as a **token quantity**, not collateral. Confirmed against a real testnet order (`scripts/verify-order-amount-semantics.mjs`): requesting `amount=5` spent **$2.575**, not $5. A user's real risk (and the payout math built on top of it) silently didn't match the number shown as "Lock Amount"/"Max Loss".
- **The fix**: `lockPosition` now sizes the order via `client.quoteBinaryStake({ marketId, side, stake })` (the SDK's own dollar-stake sizing helper — walks the book, never quotes an escrow above the requested stake) and executes it with the raw `trader.placeOrder(...)`. Typecheck, lint, the full test suite (114 tests, including 8 new ones pinning the exact bug/fix scenario in `__tests__/exchangeLockPosition.test.ts`), and `pnpm build` all pass against the new code. See `docs/API_NOTES.md` §1a for the full before/after.
- **Not yet done**: a fresh real-testnet *fill* against the new code (the same empirical method that caught the original bug). As of 2026-09-06 the indexer's registry sweep and its per-market `MarketByPk` lookup (both used on the path to `quoteBinaryStake`) are intermittently timing out badly enough — 12/12 consecutive per-market lookups failed in one scan across 578 live markets — that a full lock-and-confirm round trip couldn't be completed; one call did succeed mid-session and correctly returned a null quote for an empty book, confirming the new code path itself runs correctly against the real SDK, just not a filled order yet. This is an external indexer degradation, independent of this fix (see `docs/API_NOTES.md` §1 failure-mode table), which also currently blocks `findLiveMarket` (and therefore all real locking) app-wide. Retry with `scripts/verify-lock-position-fix.mjs` once the indexer stabilizes.

## 8. No retry/backoff on market discovery reads
- `findLiveMarket` (`exchange.ts`, called from `useLock.ts#executeLock` on every lock attempt) calls `ex.loadMarkets()` once, with no retry, backoff, or timeout shorter than the SDK's own 30s default. If the indexer's `Market` query is slow or degraded (observed directly on 2026-09-06 — see `docs/API_NOTES.md` §1), the user waits out the full 30s before seeing a generic "Somnia indexer is unreachable right now" message, with no faster feedback or automatic retry. Same gap applies to `getResolution`/`claimWinnings`'s `client.getMarket` read (the 2026-09-03 `Market_by_pk` incident). Worth a retry-with-backoff or a shorter client-side timeout if this keeps recurring, but not implemented — this app has no control over the indexer's own query performance either way.

## 9. Loss-streak cooldown, and the loss-recording gap it exposed
- **A real, pre-existing gap found while building this**: `useClaim.ts#claimPayout` only ever called `addRecentWindow` on its win/void success path — a loss returns `{ success: false }` before ever reaching that call, because there's no claim to make on a loss. So `recents` (and everything built on it — the "Win Accuracy"/"Right Calls" stats in `RecentsList.tsx`, and now this cooldown) silently only ever saw wins and voids. A user's real losses left zero trace in their own history. Fixed by adding `useClaim.ts#recordLoss`, called once from `RevealPanel.tsx` the moment a resolved, non-voided window turns out lost (guarded against the 8s resolution poll re-triggering it by checking `recents` already has that window id first).
- **The cooldown itself**: `marketService.ts#getLossStreak` counts consecutive `userResult: 'wrong'` entries at the front of `recents` (most-recent-first), resetting the instant a win or void appears. Once it reaches 3, `SideButtons.tsx` shows `LossStreakPrompt` — a **soft, dismissible** nudge ("Take a break" / "Continue anyway"), not a hard block: the whole point is friction against compulsive re-locking, not a rule that would just get routed around. Re-prompts if the streak grows further (3 → 4 → ...) but never for the same streak twice, tracked as local `acknowledgedStreak` state in `SideButtons.tsx` — not persisted, since it's meant to be a per-sitting nudge, not a permanently dismissed warning.
- **Known interaction**: because the streak is derived from `recents`, which caps at 15 entries and lives in `localStorage` (see §6), the streak is per-device like every other piece of history here — same caveat as recents' cross-device gap.
